# SentenceLens 章程

## 核心原则

### I. 跨平台一致性

**原则**: 应用程序在 Windows、macOS 和 Linux 上必须表现一致。

每个功能、服务和交互必须在所有支持的平台上无平台特定变通的情况下一致工作。必须优先使用 Electron 提供的跨平台 API 而非原生系统调用，除非绝对必要。基于 WASM 的服务（tesseract.js、sql.js）确保跨平台行为一致。

### II. 离线优先架构

**原则**: 核心功能必须在不连接互联网的情况下可用。

应用程序设计为独立的桌面工具。OCR 处理和本地数据存储使用 WASM 实现完全离线工作。LLM 功能是唯一需要外部 API 连接的组件，必须优雅地处理网络不可用情况。应用程序在离线时必须保持对阅读、整理和管理内容的功能。

### III. 集成质量

**原则**: 所有服务集成必须稳定、经过测试，并优雅地处理失败。

后端遵循清晰的服务层模式（OCR、LLM、数据库、句子分割）。每个服务必须可独立测试、具有适当的错误边界，并在外部依赖失败时提供回退行为。Express.js 后端、React 前端和 Electron 主进程之间的集成点必须具有定义良好的契约。

### IV. 可观测性

**原则**: 应用程序必须提供清晰、结构化的日志记录以便于调试和用户支持。

所有后端操作同时记录到控制台和 server.log 文件，并带有时区感知的时间戳。错误必须尽可能包含请求/会话信息的上下文。前端错误必须向用户显示可操作的消息。生产构建的日志级别必须适当（无敏感数据，合理的详细程度）。

### V. 简单性

**原则**: 实现正确解决问题的最简单解决方案。

避免过度工程化功能、抽象或架构模式。除非有明显好处，否则优先采用直接实现而非复杂模式。YAGNI（你不需要它）原则适用——不为未计划的功能构建灵活性。三层架构（Electron → Express → React）已足够，不应扩展。

### VI. 中文文档编写

**原则**: 所有项目文档必须使用中文编写。

项目面向中文用户，所有创建或更新的文档文件必须使用中文。包括但不限于：
- 项目主文档（README.md、CLAUDE.md、IMPLEMENTATION_GUIDE.md）
- Speckit 框架生成的规格、计划和任务文档
- 代码注释和字符串
- 用户界面文本

例外情况：
- 技术术语和 API 端点名称保持英文（如 HTTP、JSON、Express.js）
- 代码文件名和变量名保持英文（遵循通用编程约定）
- 第三方库的官方名称保持英文

## 技术标准

### 技术栈

- **前端**: React + Vite + TailwindCSS，构建到 renderer/ 目录
- **后端**: Express.js 在端口 8000，作为子进程从 Electron 主进程启动
- **数据库**: SQLite 通过 sql.js（纯 JS WASM），文件位于 {data_dir}/database.db
- **OCR**: tesseract.js v7，使用本地 eng.traineddata，持久化工作进程失败时使用回退工作进程
- **LLM**: OpenAI SDK v4.x，支持任何 OpenAI 兼容的端点（DeepSeek、本地 LLM 等）
- **构建**: electron-builder，使用 asar 打包（解包 server、node_modules、eng.traineddata）

### 目录结构

- main.js: Electron 主进程、窗口生命周期、服务器启动
- server/: Express.js 后端（app.js、models/、services/）
- renderer/: 已构建的 React 前端（通过 loadFile 由 Electron 加载）
- data/: 用户数据目录（可通过 UI 配置，默认为 userData/english-reading-helper/）

### API 契约

所有后端路由遵循 http://127.0.0.1:8000/api/* 处的 REST 约定。路由名称必须与原始 Python FastAPI 实现完全匹配以维护 API 兼容性。响应格式必须一致（JSON，具有适当的状态码）。错误响应必须包含可读消息。

## 开发工作流

### 代码组织

- **后端服务**: 每个关注点在 server/services/ 中（ocr.js、llm.js、sentenceSplit.js）
- **数据库操作**: 使用 sql.js 在 server/models/database.js 中集中管理
- **API 路由**: 在 server/app.js 中定义，具有清晰的路由分组
- **前端组件**: 在 frontend/src/ 中按功能组织

### 服务器进程管理

修改服务器代码时：
1. 开发模式：应用自动处理服务器重启
2. 生产模式：更改需要重新构建应用
3. 服务器日志写入到 {data_dir}/logs/server.log，并带有时区感知的时间戳

### 测试方法

集成测试对以下内容至关重要：
- 服务层契约（OCR、LLM、数据库）
- API 端点行为和错误处理
- 跨进程通信（Electron IPC → Express → React）
- 数据持久化和迁移

### 构建验证

发布前：
1. 运行 npm run build-frontend 并验证 renderer/ 已填充
2. 运行平台特定的构建命令（build-win、build-mac、build-linux）
3. 在目标平台上用干净环境测试安装程序
4. 验证离线功能（OCR、数据库、内容管理）

## 治理

此章程优先于所有其他开发实践。当此章程与其他指导原则之间出现冲突时，章程优先。

修改需要：
1. 清晰记录更改理由
2. 遵循语义化版本规则递增版本
3. 分析对现有功能和模板的影响

所有功能和错误修复必须根据这些原則进行审查：
- 是否维护跨平台一致性？
- 是否保留离线优先功能？
- 集成是否稳定且正确处理错误？
- 是否可观测和可调试？
- 是否是最简单适当的解决方案？
- 所有文档是否使用中文编写？

使用项目根目录中的 CLAUDE.md 获取运行时开发指导和技术细节。
