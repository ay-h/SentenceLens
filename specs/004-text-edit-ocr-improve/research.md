# Research: 图像预处理最佳实践和库选择

**Feature**: 文本可编辑和OCR识别优化
**Date**: 2026-04-06
**Phase**: 0 - Research

## 图像预处理流水线完整方案

基于最新 clarifications，完整的预处理流水线包含以下步骤：

```
原图 → 透视矫正 → Deskew → 自适应二值化 → 文本区域裁剪 → 锐化/降噪 → OCR
```

### 1. 透视矫正 (Perspective Correction)

**问题分析**: 手机拍照时页面不完全平行，出现上窄下宽、行不水平等问题

**解决方案**:

1. **边缘检测 (Canny)**
   - 检测图像边缘
   - 参数: threshold1=50, threshold2=150

2. **轮廓查找**
   - 寻找最大四边形轮廓
   - 过滤噪声轮廓（面积阈值）

3. **四边形拟合**
   - approxPolyDP 拟合四边形
   - 确保是4个点（四边形）

4. **透视变换 (Perspective Transform)**
   - 获取透视变换矩阵
   - warpPerspective 得到正视图

**决策**: 使用 OpenCV.js 实现完整的透视矫正流水线
**理由**:

- 处理拍照书页/试卷的标准方案
- 准确率可从60%提升至95%+
- OpenCV.js 已集成到项目

**关键参数**:

- Canny阈值: 50, 150
- 最小四边形面积: 图像面积的10%
- 透视变换插值: INTER_LINEAR

---

### 2. 自适应二值化 (Adaptive Thresholding)

**问题分析**: 拍照时中间亮、边缘暗，光照不均匀

**解决方案**:

1. **自适应高斯阈值 (Adaptive Gaussian)**
   - 局部区域高斯加权均值作为阈值
   - 适合光照不均匀文档

2. **参数调优**
   - blockSize: 31 (邻域大小，奇数)
   - C: 15 (从均值减去的常数)

**决策**: 使用 OpenCV.js adaptiveThreshold (ADAPTIVE_THRESH_GAUSSIAN_C)
**理由**:

- 比全局阈值更适合光照不均
- 比自适应均值效果更好（边缘更平滑）

---

### 3. 文本区域检测与裁剪 (Text Region Detection)

**问题分析**: 页边、阴影、手指会干扰OCR识别

**解决方案**:

1. **边缘密度分析**
   - 检测文本区域边缘密度
   - 区分文本区域和背景

2. **MSER (最大稳定极值区域)**
   - 检测文本字符区域
   - 合并为文本行/段落

3. **主区域提取**
   - 选择最大文本区域
   - 添加适当边距（20px）

**决策**: 使用边缘密度+形态学操作检测主文本区域
**理由**:

- 无需训练模型
- 适合规则文档布局
- 计算速度快

---

### 4. 预处理智能跳过逻辑

| 检测条件   | 跳过步骤     | 检测方法              |
| ---------- | ------------ | --------------------- |
| 无透视变形 | 透视矫正     | 四角接近矩形，变形<2° |
| 无歪斜     | Deskew       | 投影法角度<0.5°       |
| 光照均匀   | 自适应二值化 | 灰度直方图标准差<阈值 |
| 无干扰边缘 | 文本区域裁剪 | 边缘文本密度检测      |
| 清晰无噪   | 锐化+降噪    | 边缘清晰度检测        |

## 图像预处理技术研究

### 图像歪斜校正

**问题分析**: 拍摄试卷/书本时，纸张不平导致图像歪斜，影响 OCR 识别

**解决方案**:

1. **Hough Transform (霍夫变换)**
   - 使用霍夫变换检测图像中的直线（文本行）
   - 计算直线角度，旋转图像使其水平
   - 适用于有明显文本行的文档
   - 实现：opencv.js 或手动实现简化版本

2. **投影法 (Projection Profile)**
   - 计算不同旋转角度下的水平投影
   - 选择具有最大投影峰值的旋转角度
   - 计算量小，适合实时处理
   - 对文档图像效果好

**决策**: 使用投影法进行歪斜校正
**理由**:

- 计算量小，适合 Node.js 环境
- 对文档图像效果好
- 可以使用纯 JavaScript 实现或轻量级库

### 图像对比度和亮度调整

**问题分析**: 明暗不均匀的照片影响 OCR 识别

**解决方案**:

1. **直方图均衡化 (Histogram Equalization)**
   - 增强图像对比度
   - 适用于低对比度图像
   - 可能过度增强噪声

2. **CLAHE (限制对比度自适应直方图均衡化)**
   - 局部对比度增强
   - 避免全局直方图均衡化的过度增强
   - 更适合 OCR 预处理
   - 实现：opencv.js

3. **自适应阈值化 (Adaptive Thresholding)**
   - 根据局部区域调整阈值
   - 适用于光照不均匀的文档
   - 实现简单，纯 JavaScript 可实现

**决策**: 使用 CLAHE 进行对比度调整
**理由**:

- 对光照不均匀文档效果最佳
- 避免过度增强噪声
- opencv.js 提供现成实现

### 图像锐化

**问题分析**: 模糊图像影响 OCR 识别

**解决方案**:

1. **Unsharp Mask (非锐化掩模)**
   - 从原图减去模糊版本
   - 增强边缘
   - 参数可调（强度、半径）
   - 实现：opencv.js 或纯 JavaScript

2. **拉普拉斯算子**
   - 边缘检测算子
   - 可以锐化图像
   - 实现：opencv.js

3. **高斯差分**
   - 减去两个高斯模糊版本（不同 sigma）
   - 保留高频信息（边缘）
   - 适合自然图像

**决策**: 使用 Unsharp Mask 进行锐化
**理由**:

- 参数可调，适合不同模糊程度
- 可以控制锐化强度，避免过度锐化
- 纯 JavaScript 实现相对简单

### 图像降噪

**问题分析**: 噪点影响 OCR 识别

**解决方案**:

1. **中值滤波器**
   - 替换每个像素为中值
   - 有效去除椒盐噪声
   - 实现简单，纯 JavaScript

2. **高斯模糊**
   - 平滑图像，减少噪声
   - 可能导致图像模糊
   - 需要控制模糊程度

3. **双边滤波 (Bilateral Filter)**
   - 保留边缘的同时平滑图像
   - 适合 OCR 预处理
   - 实现：opencv.js

**决策**: 使用双边滤波进行降噪
**理由**:

- 保留边缘信息，对 OCR 重要
- opencv.js 提供现成实现
- 效果优于简单的高斯模糊

## 图像处理库选择

### 候选库

1. **opencv.js**
   - OpenCV 的 JavaScript 绑定
   - 功能全面，性能良好
   - 支持所有需要的预处理算法
   - 下载大小：~10MB (主要 WASM)
   - 优势：功能全面，官方维护
   - 劣势：体积较大

2. **sharp**
   - 高性能 Node.js 图像处理库
   - 基于 libvips
   - 支持基本操作（调整大小、锐化、调整）
   - 不支持高级算法（歪斜校正、双边滤波）
   - 下载大小：~5MB
   - 优势：性能好，API 简单
   - 劣势：不支持高级算法

3. **jimp**
   - 纯 JavaScript 图像处理库
   - 无原生依赖，易于打包
   - 性能较低
   - 下载大小：~2MB
   - 优势：纯 JavaScript，易于打包
   - 劣势：性能低，功能有限

4. **自研轻量级预处理**
   - 针对 OCR 优化的简化算法
   - 纯 JavaScript 实现
   - 减小依赖
   - 下载大小：<100KB
   - 优势：离线打包友好，针对性优化
   - 劣势：需要开发和测试

**决策**: 使用 opencv.js
**理由**:

- 功能全面，支持所有需要的预处理算法
- 性能良好，适合图像处理
- 官方维护，文档完善
- 可以通过 asarUnpack 配置正确打包
- 符合离线打包原则（作为 WASM 捆绑）

## 统一翻译按钮设计

### 用户界面设计决策

**问题**: 用户询问是否可以合并"翻译"和"智能翻译"按钮

**澄清结果**: 合并为单个翻译按钮，自动检测变化并只翻译需要翻译的句子

**技术方案**:

1. **智能翻译逻辑**
   - 检测哪些句子需要翻译（新增或修改的句子）
   - 跳过已有翻译且未变化的句子
   - 无变化时显示友好提示

2. **按钮状态管理**
   - 始终显示"翻译"按钮文本
   - 根据文本变化状态调整行为
   - 提供清晰的用户反馈

3. **用户体验优化**
   - 减少界面复杂度
   - 避免用户选择困惑
   - 保持智能翻译的效率优势

**决策**: 采用统一翻译按钮设计
**理由**:

- 简化用户界面，降低认知负荷
- 自动检测变化，用户无需手动选择
- 保持智能翻译的核心优势
- 符合用户直觉的操作流程

## 句子级别变更检测

### 技术方案

1. **句子分割服务扩展**
   - 现有 `server/services/sentenceSplit.js`
   - 扩展为可导入模块
   - 新增 `detectChanges(oldText, newText)` 方法
   - 返回：`{ changed: boolean, affectedSentences: [] }`

2. **句子哈希比较**
   - 对每个句子计算哈希值
   - 比较新旧哈希值检测变化
   - 快速、简单
   - 实现：Node.js crypto 模块

3. **简单文本比较**
   - 逐句比较文本内容
   - 忽略标点和空格差异（可选）
   - 简单、直观
   - 实现：纯 JavaScript

**决策**: 扩展现有句子分割服务，使用简单文本比较
**理由**:

- 复用现有服务
- 简单文本比较足够检测句子变化
- 避免不必要的哈希计算
- 易于理解和维护

## OCR 结果质量评估

### 技术方案

1. **Tesseract 置信度分析**
   - tesseract.js 返回每个单词/字符的置信度
   - 计算平均置信度
   - 标记低置信度单词
   - 阈值：0-100，通常 <60 需要检查

2. **单词字典验证**
   - 将识别单词与英文词典对比
   - 统计非字典单词比例
   - 阈值：非字典单词 >20% 可能质量低

3. **文本长度和空行分析**
   - 检测异常短的行或空行过多
   - 可能表明识别问题
   - 阈值：空行 >30% 可能质量低

**决策**: 使用 Tesseract 置信度分析
**理由**:

- 直接来自 OCR 引擎
- 准确反映识别质量
- 实现简单
- tesseract.js 已返回此信息

## 文本编辑界面布局优化

### 用户界面设计决策

**问题**: 用户反映编辑时句子无换行排版，不利于阅读和定位修改

**澄清结果**:

- 布局模式：句子级独立编辑模式，每个句子独立显示并支持单独编辑
- 视觉反馈：修改的句子高亮显示，未修改句子保持正常样式
- 间距分隔：适中间距（8-12px），无分隔线
- 交互方式：编辑按钮与分析句子按钮放在一起，点击进入编辑模式

### 技术方案

1. **句子级独立编辑组件**
   - 每个句子作为独立的 React 组件
   - 支持单独编辑状态管理
   - 保持句子间的视觉独立性

2. **修改状态可视化**
   - 使用 CSS 类或样式控制高亮显示
   - 比较编辑前后内容检测变化
   - 实时更新视觉状态

3. **响应式间距设计**
   - 使用 CSS Flexbox 或 Grid 布局
   - 8-12px 的句子间距
   - 适配不同屏幕尺寸

4. **按钮集成设计**
   - 编辑按钮与分析按钮并列
   - 保持现有按钮样式一致性
   - 避免与单击选中、双击翻译冲突

**决策**: 采用句子级独立编辑布局
**理由**:

- 直接解决排版和定位问题
- 符合用户对清晰阅读体验的需求
- 与现有交互模式保持一致
- 便于实现句子级别的变化检测
